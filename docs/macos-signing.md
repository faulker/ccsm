# Signing the macOS release binaries

The release workflow (`.github/workflows/release.yml`) codesigns and optionally
notarizes the two macOS binaries. Everything is opt-in: when the secrets below
are missing, the macOS jobs still build and publish, they just ship unsigned
binaries the way they always did. So you can add the certificate first and
notarization later.

Signing happens after `cargo build` and before the tarball is created, so the
`checksums-sha256.txt` published with the release covers the signed binary.
ccsm's self-updater (`update.rs`) verifies downloads against that file, so
those two steps must stay in that order.

## What you need from Apple

A **Developer ID Application** certificate. This is the one that matters. An
"Apple Development" or "Mac Development" certificate will sign the binary but
will not satisfy Gatekeeper on anyone else's Mac, so it is not worth shipping.

1. In [the Apple Developer certificates
   console](https://developer.apple.com/account/resources/certificates/list),
   create a certificate of type **Developer ID Application**. You need to be the
   Account Holder of the team, and you will upload a CSR generated by Keychain
   Access (Certificate Assistant → Request a Certificate From a Certificate
   Authority, saved to disk).
2. Download the resulting `.cer` and double-click it to install it into your
   login keychain.
3. In Keychain Access, find **Developer ID Application: <your name> (TEAMID)**,
   expand it so both the certificate and its private key are selected, then right
   click → **Export 2 items…** and save a `.p12`. Choose a password; you will need
   it in a moment.
4. Base64 the `.p12` so it can live in a GitHub secret:

   ```sh
   base64 -i DeveloperID.p12 | pbcopy
   ```

## Repository secrets

Add these under **Settings → Secrets and variables → Actions → Repository
secrets** (`gh secret set NAME` works too).

| Secret | Value |
| --- | --- |
| `APPLE_CERTIFICATE_P12` | The base64 from step 4 above. |
| `APPLE_CERTIFICATE_PASSWORD` | The password you chose when exporting the `.p12`. |
| `APPLE_SIGNING_IDENTITY` | The identity's full name, e.g. `Developer ID Application: Winter Faulk (AB12CD34EF)`. Copy it from `security find-identity -v -p codesigning`. |

That is enough for signing. The `Report signing status` step prints
`codesign --display` output into the run summary, so you can confirm it worked.

## Notarization (optional, adds three more secrets)

Signing on its own is enough for `curl`-installed binaries, but a binary
downloaded through a browser gets a quarantine flag, and Gatekeeper will refuse
to run it until the release is notarized. Notarization needs an App Store Connect
API key, which (unlike an app-specific password) does not expire.

1. In [App Store Connect → Users and Access →
   Integrations](https://appstoreconnect.apple.com/access/integrations/api),
   create a team key with the **Developer** role. Download the `.p8`; Apple only
   lets you download it once.
2. Note the **Key ID** shown next to it, and the **Issuer ID** shown above the
   key list.
3. Add three more secrets:

| Secret | Value |
| --- | --- |
| `APPLE_NOTARY_KEY` | `base64 -i AuthKey_XXXXXXXX.p8` output. |
| `APPLE_NOTARY_KEY_ID` | The Key ID, e.g. `XXXXXXXXXX`. |
| `APPLE_NOTARY_ISSUER_ID` | The Issuer ID (a UUID). |

The workflow zips the signed binary purely to submit it (`notarytool` accepts
zip, pkg, and dmg, not tar.gz) and throws the zip away afterwards. The ticket is
not stapled: a bare executable has nowhere to staple to, so Gatekeeper looks the
ticket up online using the signature's hash. Nothing about the published
`.tar.gz` assets or their names changes.

## Verifying a release

On a Mac that has never seen your certificate:

```sh
codesign --verify --strict --verbose=2 ./ccsm    # signature is intact
spctl --assess --type execute -vv ./ccsm         # Gatekeeper's verdict
```

`spctl` reporting `source=Notarized Developer ID` means both halves worked.
